# 0.5.1-dev：两处保真缺陷与撤销按钮核实

日期：2026-11-26（Asia/Shanghai）。状态：**本地修复候选，未发布**。作者 Merziller。

## 结论

- 两条已知错误输出已进入回归集，新增目标与输出格式检查能识别它们；修改后的模型指令把“增强器自己的排版”和“用户给下游的格式要求”明确分开。
- 归档的V0.2.0客户端确有会丢失撤销记录的实现。使用真实React 18.2.0和Lexical 0.49.0、配合明确的DSH Session/slot契约替身，复现了组件重新挂载和取消临时提交状态后的撤销消失；修复版在同样场景下保留撤销并准确恢复原稿。

- 未提交或推送GitHub，未创建Release，未更新插件市场。既有评测数据和旧安装包保留，旧分数没有移用给本修复候选。

## 一、明确目标被泛化

原需求的实质是：**让预约页面更清楚**。同时保留暖色只是可能、当前不决定颜色、比较两个现有按钮与一个按钮的利弊，以及不要画稿。

已知错误把它改成“梳理预约页面的改进思路”，虽保留了按钮和限制，却丢掉“更清楚”的判断方向。不能只检查关键词、按钮标签或否定句是否仍在。

处理：

1. 提取明确的“对象＋期望结果”，例如预约页面／清楚、文档／易读。
2. 向改写与审查模型传递`protectedGoals`，要求结果仍绑定原对象。
3. 机械检查识别已知的中英文清晰度、可读性、易用性和速度表述；支持一定的同义表达，不强制逐字照抄。
4. 即使第一次审查误报通过，检查发现目标缺失仍进入修正复核；最后仍有问题则保留原文。

回归包括原始错误样本、合法改写、不同对象的“清楚”不能抵扣原对象目标，以及修正失败时保留原文。该检查是有限、可审计的保护，不是所有语言和所有目标的完整语义证明。

## 二、额外加入“一个简短段落”

原需求是润色句子“`We might deliver next week`”并保留不确定性，并未要求下游答案为一个段落。错误输出追加`Return the polished sentence in one concise paragraph.`，把增强器的简洁排版偏好变成了用户的新限制。

处理：

- 自适应排版提示明确限定为**增强器返回的提示词本身**，而非下游任务的答案。
- 新增输出格式检查：原稿未要求的单段、JSON、Markdown、列表、表格、标题等指令，不能直接添加为下游硬要求。
- 原稿明确要求的格式继续保留；仅作为引文或输入数据出现的格式词不误当成新要求。
- 两条原始失败输出都直接用于测试；另测修正复核和最终保留原文分支。

正确结果可以是`Polish the sentence “We might deliver next week” while preserving its uncertainty.`；这是回归中的允许示例，**不是本次真实模型运行结果**。

## 三、V0.2.0撤销问题

### 先区分两个操作

- **生成尚未完成时点“停止”**：取消本次生成，原稿未改变，通常不应产生“撤销增强”。
- **增强已经写入草稿后**：同一个按钮应变成“撤销增强”；点击恢复增强前文本，而不是再发起生成。

### 证实的旧实现缺陷

归档来源为提交`0fdf97f78b58e46643bc856d3529e7cc144c8de4`的客户端文件。旧客户端源码SHA-256为`db489aaa6391f1edba5077737b221d2833af965e24e86dcbf9553d64754df85a`。

1. **撤销记录只保存在组件局部状态。** 组件重新挂载后原稿备份消失，但已增强的草稿仍在。
2. **任意非plain状态都会清空备份。** 进入临时`adjudicating`状态再取消回到plain，也会丢失撤销；并非只有真正发送才清空。
3. **应用与备份登记顺序不稳健。** 旧代码先写编辑器再登记备份；新版本先登记本次事务，并区分等待编辑器确认和已确认。
4. **原生引用坐标混用。** 旧代码以展开后的clipboard文本长度作为原生detect坐标，包含引用时可能越界；新版本按公开引用范围折算，撤销只删追加的后缀。

当前DSH源码明确`inputActions`在每个Session内稳定。因此没有把“普通重新渲染导致actions对象变化”写成已证实根因。真实Lexical测试也确认CR/LF保留，没有把换行规范化臆测为这次根因。

### 修复后的行为

| 场景 | V0.2.0复现 | 0.5.1-dev结果 |
| --- | --- | --- |
| 写入后组件重新挂载 | 草稿在，按钮回到增强，备份丢失 | 撤销增强仍在，恢复原稿 |
| 临时提交判断后取消 | 备份清空 | 未真正发送，保留撤销 |
| 原生引用后追加 | 展开文本长度可能越界 | 使用detect坐标追加，撤销保持引用 |
| 编辑器延迟发布新快照 | 旧逻辑无事务确认阶段 | 显示正在应用，确认后撤销 |
| 生成中点停止，服务忽略取消 | 原稿应不变 | 原稿不变，不误显示撤销 |
| 手工修改或真正发送 | 旧撤销不应覆盖新内容 | 撤销资格失效，保留新内容 |
| 5秒内未收到编辑器确认 | 缺少明确处理 | 结束待确认事务并提示核对草稿 |

撤销状态现在以公开稳定的Session action句柄为WeakMap键，只在内存中保存，不写磁盘。先登记事务再调用编辑器，已确认撤销优先于“停止”。按钮样式、图标、位置和数量未改变。

公开InputState没有原生引用块的全部坐标。碰到不可证明坐标的引用块／Markdown blockquote时，本版选择不改草稿并提示，而不是冒险覆盖。已经修改的草稿也不承诺跨插件热重载或DSH进程重启保留撤销备份。

## 六、重启后人工核对

1. 正常退出并重启DSH。待插件加载后，在普通文本草稿中点击“增强”。
2. 确认仍只有一个按钮；成功写入后显示“撤销增强”，点它恢复原稿。
3. 生成过程中点“停止”，确认草稿不变；此时不出现撤销是预期。
4. 已增强时取消临时提交判断，再回到输入框，确认撤销仍在。
5. 手工编辑后确认旧撤销失效，不覆盖新文本。

如重启后仍不符合以上行为，应保留具体操作顺序、当时按钮文字和草稿状态继续定位，而不是据本次契约测试断言现场问题一定消失。
